1. О проекте
Проект демонстрирует развёртывание системы обнаружения сетевых вторжений Suricata в виртуальной лаборатории Oracle VirtualBox.
В ходе работы настроены сетевой захват, собственные сигнатуры, анализ событий и уведомления в Telegram.
Тестирование выполнялось исключительно в разрешённой лабораторной среде.

3. Цели лаборатории
•	Разобраться в принципах работы IDS и сетевого мониторинга.
•	Научиться писать и проверять собственные правила Suricata.
•	Отрабатывать контролируемые проверки HTTP GET/POST и ICMP.
•	Реализовать передачу выбранных предупреждений в Telegram.
•	Понять ограничения мониторинга через виртуальные и физические сетевые интерфейсы.

4. Компоненты
Компонент                        Назначение

Kali Linux                       Генерация тестового трафика и проверка обнаружений
Ubuntu 22.04 + Suricata 8        IDS: захват пакетов, сопоставление с правилами, запись событий
Victim / Zabbix                  Тестовый веб-сервер и веб-форма для HTTP-запросов
Oracle VirtualBox                Изолированная виртуальная сеть и сетевые адаптеры
Python monitor.py + Telegram     Отправка выбранных событий из eve.json в Telegram

4. Архитектура сети
Исходная проверенная топология IDS:
Kali Linux (10.77.0.10) ── VirtualBox intnet ── Victim / Zabbix (10.77.0.20)
                                   │
                         Ubuntu + Suricata
                         enp0s8: захват intnet
                         enp0s3: домашняя сеть 192.168.0.x

В лабораторной сети intnet: Allow All даёт Suricata возможность получать трафик между другими виртуальными машинами. 
Подключение enp0s3 к домашней подсети не гарантирует наблюдение за соединениями между всеми Wi-Fi клиентами.

5. Конфигурация Suricata
Главный файл — /etc/suricata/suricata.yaml. В нём задаются переменные HOME_NET, интерфейсы AF_PACKET, пути к правилам и параметры журналирования.
HOME_NET: "[192.168.0.0/16,10.77.0.0/24]"

af-packet:
  - interface: enp0s8
    cluster-id: 99
    cluster-type: cluster_flow
    defrag: yes

Это фрагмент настройки, а не полный suricata.yaml. При использовании нужно сохранять остальные необходимые параметры установленной версии Suricata.
sudo suricata -T -c /etc/suricata/suricata.yaml
sudo systemctl restart suricata
sudo systemctl status suricata --no-pager

6. Собственные правила обнаружения
Правила находятся в /etc/suricata/rules/local.rules. Для собственных сигнатур использованы отдельные SID
Фактический файл rules/local.rules в GitHub является источником истины для используемых SID и сообщений.
При изменении правил обязательна повторная проверка через suricata -T.

7. Проверка трафика и журналов
В рамках лаборатории использовались ping, curl и tcpdump. Для контролируемых HTTP-проверок запускался простой сервер Python на Victim.
python3 -m http.server 8888 --bind 10.77.0.20
curl "http://10.77.0.20:8888/?q=union"
curl "http://10.77.0.20:8888/?q=select"
curl -X POST -d "query=SELECT" http://10.77.0.20:8888/
sudo tcpdump -ni enp0s8 tcp
sudo tail -n 0 -F /var/log/suricata/fast.log

Проверки через реальную веб-форму Zabbix показали важность различия между HTTP URI и телом POST-запроса: для них применяются разные буферы анализа Suricata.
8. Telegram-уведомления
Python-скрипт monitor.py читает новые события из /var/log/suricata/eve.json, выбирает нужные alert по идентификаторам сигнатур и отправляет сообщения в Telegram. Настройки хранятся в .env, который нельзя публиковать.
BOT_TOKEN=YOUR_BOT_TOKEN
USERS=YOUR_TELEGRAM_USER_ID
ATTACK_IDS=1000002,1000003,1000004,1000005
IGNORED_ATTACK_IDS=
PRIORITY=

После изменения .env процесс monitor.py необходимо перезапустить, так как переменные читаются при старте. 
Монитор пропускает уже существующие записи eve.json при запуске, поэтому для проверки нужно создать новое событие.
Telegram-компонент monitor.py основан на открытом проекте bugourmet/suricata-alerts: https://github.com/bugourmet/suricata-alerts . 
Исходному автору принадлежит разработка оригинального монитора.
